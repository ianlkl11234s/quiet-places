# Blender 場景製作與網頁移植計畫

日期：2026-09-07。狀態：**規劃完成，待使用者確認後實作**。
規劃分支：`plan/blender-scene-pipeline`，起點 `3416f7c`。

本輪只建立規劃分支、做能力／連線探測與撰寫文件；不製作正式模型、不修改應用、不開始動畫或高品質渲染。使用者已停止過夜排程，不重新啟用。測試結果見 [BLENDER_PREFLIGHT.md](BLENDER_PREFLIGHT.md)。

## 1. 目標與交付判準

以使用者提供的 `ChatGPT Image Sep 7, 2026, 12_24_56 AM.png` 為樹影參考：高挑而安靜的石材房間，右側高窗，枝葉遮住部分陽光，光斑跨越牆面與地面，暗部仍能看出材質，空氣中有克制的斜向光束。參考是視覺目標，單張圖無法唯一反推出真實尺寸或光源參數。

作品必須在**靜止畫面**就有相同的空間秩序與光影層次；動畫只增加生命感。不得以「有樹、有窗、有光、有魚」或 build 通過替代美術驗收。

完成後交付：

- 樹影午後與海光之室的可編輯 `.blend` 母檔、材質／貼圖、相機、燈光配置、輸出腳本與資產清單。
- 一尾經驗收的錦鯉模型、骨架、循環游泳片段，再衍生少量花紋與群體變化。
- 網頁用 GLB／貼圖／場景設定，沿用 Quiet Places 的切換、四時段、音樂、暫停、畫質與圖片輸出。
- Blender 與網站同鏡頭、同時刻的比較圖片，以及網站的兩景 × 四時段 PNG／ZIP。Blender 宣傳渲染與實際網頁輸出須清楚區別。
- 可回退的分段 commits、效能與視覺驗收記錄。不上傳 GitHub、不部署，除非後續另有指示。

原水光與雨景保留。兩個新場景的既有版本作為可回退基準，不再視為視覺驗收合格。

## 2. 路線決策

採 **Blender 製作 + Three.js 即時呈現**。固定主鏡頭先達標，再驗收目前窗景左右各 15° 的有限環繞；不自動縮成一張背景圖或影片，也不擴充自由漫遊。

Blender 負責形體、真實尺度、UV、PBR 材質、枝葉結構、魚骨架、相機、離線光照基準；網頁負責動態直射光／陰影、輕量空氣光、風、海面、游動路徑、時段和互動。靜態間接光可預先計算，动态葉影不可烘死在底色內。

**最小垂直切片是樹影日間的一面窗、一組枝葉、一片有材質的牆地。** 先證明它能從 Blender 到網站保持品質，再擴充完整房間。不能做完整個高模場景，最後一天才測匯出。

如果網頁品質／效能無法同時達標，依序降低細節、縮減陰影覆蓋、降低體積光解析度與更新頻率。若最終必須改成预渲染影片或限制視角，須把品質與互動取捨交給使用者選擇，不自行替換產品方向。

## 3. 樹影午後：製作標準

### 構圖與建模

1. 先依參考圖標示窗角、牆角、牆地交線、亮斑範圍與光束方向；使用 2:3 直幅主鏡頭。尺寸從公尺尺度建立並記錄，圖中比例優先於猜測絕對尺寸。
2. 房間是真實封閉空間，包含窗洞厚度與窗台、微小倒角；檢查陽光只能經開口進入，無漏光。初版不加玻璃，先排除不必要的反射／透射問題。
3. 石材用低頻色差、中頻粗糙度與細微法線共同表現，不用單層均勻噪聲取代材質。地面較平滑，仍非鏡面。
4. 樹幹、主枝、細枝與葉叢有連接關係；葉片有大小、朝向、厚薄與疏密差異。近景葉片保留輪廓，遠景用合併／實例化的葉叢，不以滿窗隨機貼片替代枝葉。

### 光照

- Blender 基準：窗外日光與天空環境，完整房間遮蔽；無室內燈具、無隱藏室內補光。以外部光線反彈形成暗部細節。
- 網頁主方向光負責窗框與枝葉陰影。`RectAreaLight` 不能投影陰影，因此不再讓它擔任唯一核心光源；見來源 [S1]。
- 使用同一太陽方向、同一枝葉動作來產生表面陰影。空氣光須取用一致的開口與遮蔽資訊；不能用與樹葉無關的隨機條紋另畫光束。
- 先測普通動態陰影，再測低解析度體積散射。若透明葉片需要 alpha-test，陰影 pass 與可見材質必須使用相同 alpha 閾值／變形。
- 烘焙間接光時隔離直接光與動態葉影；保留光照來源記錄，避免貼圖和即時燈光重複照亮。AO 只做接觸遮蔽，不把整個房間塗黑。
- 體積光應由散射與遮擋形成，低密度開始；不靠提高 bloom 把空氣變成白霧。窗外高亮允許局部接近白色，但葉片邊緣與窗框仍可辨識。

### 微風

用主枝低頻彎動、次枝延遲、葉片小幅旋轉形成不同尺度的運動。先做 10–15 秒循環測試片段，檢查接縫、重複感與葉影同步。骨架與少量節點動畫優先；若改用 shader 變形，深度／陰影材質也必須同步變形。首版不做整棵樹的昂貴物理求解。

## 4. 錦鯉：獨立資產與動態

先做單尾，不能用大量魚掩飾單體問題。模型需有收窄的尾柄、嘴部、嵌入頭部的眼睛、連接魚身的胸鰭與背鰭；花紋在貼圖上，不是浮在表面的幾何塊。避免高飽和玩具塑膠感，也不靠自發光讓魚在黑暗中發亮。

以少量骨骼控制頭部、軀幹、尾柄與尾鰭，胸鰭獨立小幅動作。製作慢速直游循環；转向由路徑曲率驅動身體彎曲與方向，不能整尾剛體旋轉。

網頁把「魚自身動畫」與「地面路徑」分離：骨架／片段來自 Blender，速度、路徑、邊界與相位由應用控制。保留目前 FloorKoi 的邊界／暫停語意，但替換其橢圓外形及裝飾性陰影。

地面高度以新房間 metadata 為準；限制整個魚身包圍體（含魚鰭），不只限制原點。魚底部與地板保持小距離、不能穿地或突然上下浮動；高度投影與柔和陰影要匹配。先一尾通過，再逐步增加至約 5–7 尾並檢查重疊、避讓、轉彎與不同動作相位。貼地漂浮是超現實設定，形體與光照仍應可信。

## 5. 海光之室

沿用已驗證的材質、曝光、相機与資產流程，另做低而寬的窗、窗台與海平線構圖；不是只把樹換成海貼圖。

海面保留在窗外：大尺度緩慢起伏搭配較小的方向波和細部法線，波浪幾何與反射法線一致，遠处做頻率衰減以避免條紋／閃爍。以天空與太陽反射為主，不先加入暴風、泡沫或完整 GPU 流體。

海面向室內反射的光必須有可解釋的方向與窗口裁切。參考圖地板大片焦散可能含藝術誇張，先建立可信的柔和反射，再做受控藝術增強；不能把不相干的發光網格當成物理焦散。錦鯉沿用同一資產，但路徑適配新房間。

## 6. Blender → 網頁資產契約

| 類別 | 約定與驗證 |
|---|---|
| 尺度／方向 | Blender 公尺、套用適當 transforms；依 glTF 匯出器進行 Z-up → Y-up，不在 loader 再重複旋轉；骨架不能在綁定後任意套用 transform |
| 節點命名 | `Room`、`WindowFrame`、`TreeRig`、`LeafCanopy`、`KoiRig`、`Camera_Hero`；場景 metadata 包含地面高度、窗洞、可游範圍與相機約束 |
| 材質 | Principled BSDF 對應 glTF 支援的 PBR；底色 sRGB，normal／roughness／metallic／AO 用正確非色彩資料處理；程序材質烘成貼圖，不預期節點自動搬移 |
| 光照貼圖 | AO 與間接光分開；間接 lightmap 不當成 glTF 自動支援，另用資產 manifest 綁定對應 UV／texture，先完成一面牆的匯入試驗 |
| 動畫 | 命名 clips 與起訖時間；用 exporter 支援的骨架／shape key／transform 動畫，不預期 Geometry Nodes、模擬快取或 constraints 原样播放 |
| 實例化 | 先驗證 exporter 與既有 Three 版本對 instancing 的實際相容性；不能只看 Blender 物件數推估網頁 draw calls |
| 光源／體積 | Blender 面光與 Cycles 體積效果不當作 GLB 完整攜帶的功能；在網頁重建並用同鏡頭比較 |
| 色彩 | 保存 Blender view transform、曝光、光源及材質設定；目前網頁 ACES 不等於 Blender AgX。用校色測試與同一線性材質基準確定轉換方案，避免雙重 tone mapping；不能為新景隨意改掉原水光曝光 |
| 生命週期 | Mixer 停止、動畫 uncaching、材質／幾何／貼圖依 ownership 釋放；共用貼圖需明確引用管理，不能先被另一場景 dispose |

GLB 支援的模型、材質、骨架與 shape key 匯出範圍見 [S2]；實際以 Blender 5.1.2 和 repo 鎖定的 Three 0.180.0 做端到端驗證，不以最新文件取代版本測試。

擬定檔案分工（未建立正式資產）：

- `assets/blender/leaflight.blend`、`oceanlight.blend`、`koi.blend`：可編輯母檔，貼圖使用相對路徑並驗證重新開檔無遺失。
- `assets/blender/scripts/`：可重現匯出腳本，從明確檔案執行，不操作使用者未保存的互動場景。
- `public/models/`、`public/textures/`：經網頁預算限制的輸出；每個資產有來源、用途、授權、版本與雜湊。
- `src/places/catalog.ts`：保留既有入口；非同步準備 GLB 後才切換，新增場景實作回傳現有 `PlaceInstance`。
- 新 Blender 場景 adapter 擁有 loader／Mixer／lightmap／shader，不把它們散入 `main.ts`。新資產載入失敗要保持可用的上一景與重試入口，不先 dispose 再讓畫面壞掉。
- `exports/blender-review/` 與驗收紀錄：同鏡頭對照、局部細節、時段與性能結果。

已有 music、preferences、場景選單、30/24 fps 上限與背景暫停保留。輸出時定義固定 seed、sample time 與動畫取樣方式，不能依載入時間決定魚的位置。

## 8. 四時段照明策略

首選先完成一個日間基準，不把四組 full lighting 烘到四套底色。直射光、葉影與天空即時驅動；間接光先比較兩個策略：單一中性間接基底隨外光調整，或每時段獨立間接 lightmap 並在相鄰時段混合。以夜景殘光、顯存與切換結果決定，記錄 ADR，不先承諾全部載入。

四個標準時刻沿用既有 UI，但現在的 `intensity/warmth/angle/activity` 不足以唯一表達真實窗光方向；新景以獨立時段設定提供 sun direction、外光色、曝光基準與天空參數，避免改壞水光。任意時間滑桿需在已驗證的關鍵時段間平滑插值；月光時段不宣稱天文準確。

## 9. 驗收清單與建議效能預算

**視覺為首要門檻，以下數值是待量測的工程目標，不是既有結果。**

- 主鏡頭固定 1024×1536，與參考圖並排查看；再檢查 1280×720 橫幅及左右各 15° 端點。
- 比較窗角、牆角、地平線等主要輪廓；白模階段關鍵點偏差目標不超過畫幅約 5%，審美由人工確認。
- 五項必須通過：空間比例、石材細節、光源／遮擋一致、暗部可讀、無貼紙式投影。保留至少牆面、窗框、地板三個 100% 局部對照。
- 三張證據並列：參考圖、Blender hero、網頁同鏡頭；不可用 Cycles 輸出冒充網站效果。SSIM 等圖像數值不能代替不同場景的藝術判斷。
- Standard 目標 30 fps、low 24 fps；短時 60 秒量測 frame interval p95 ≤40/50ms，記錄視窗、DPR、機型、GPU、browser，不報理論 fps。
- 初始單景下載目標 ≤15 MB（模型、貼圖及必要 lightmaps 全部算入），壓縮前後另列；可見三角形目標 ≤150k、draw calls ≤100，超標先定位實際瓶頸而非盲減面。
- 紋理先以 1K–2K 為主、估計含 mipmaps GPU texture memory ≤192 MB；GLB 壓縮大小不代表顯存。不能同時保留八套高解析光照。
- 靜态地面不必每幀計算；動態 shadow map 初始 1024／2048，依陰影覆蓋面積與設備驗證。葉片 overdraw、陰影 pass、體積光分別計時。
- 反覆切換 10 次無持續增长的 texture／geometry 數量；allow 固定 renderer cache，不要求記憶體瞬間歸零。失敗載入、快速連續切換、再載入均可恢復。
- 背景停止繪圖，暫停後停止自然動畫但允許操作重繪；匯出完成回到原場景／時刻／視角。音樂不可自動播放。
- Blender 探索先用小解析度、低 samples、單張，不同時跑多個渲染。Metal／GPU 必須先讀回和小圖實測；不可因已安裝就宣稱加速可用。不啟動整夜渲染或重新建立排程。
- 驗證後關閉本任務的預覽／背景測試程序，不關閉使用者原本的 Blender 或其他應用；保留 dev server 的必要使用情境。

## 10. 分工、版本與风险處理

主 agent：參考圖解讀、構圖與光照決策、資產契約、Blender／網站對照、最後驗收。Terra：有檔案 ownership 的模型腳本、單魚資產流程或場景 adapter。Luna：資產命名／來源清單／雜湊、export checklist、確定性 smoke。最多兩個有独立工作可做的 worker 同時運作；同一 `.blend` 不多人寫。

主線 `3416f7c` 保留。此分支只保存規劃，獲確認後再從本計畫建立實作分支；每個通過階段提交程式、匯出設定與必要小型資產。大型 `.blend`／原始貼圖採版本化可恢復保存，若需 Git LFS，先確認本機及 remote 支援，再加入大檔，不能把普通 Git tag 當成未提交檔案的備份。

| 風險 | 應對 |

| MCP 已裝但本任務不可用 | 先定位 add-on 與 server 設定，不擅自裝別的第三方插件。P0 讀回測試未通前，不宣稱可控制正在開啟的 Blender |
| Blender 成圖漂亮、網站品質流失 | P2 強制早期 glTF 垂直切片，校色與陰影同場景對照；未通過不量產 |
| 陰影與葉子各動各的 | 主日光與枝葉變形共用；自訂風 shader 必須同步 shadow/depth pass，否則先用骨架動畫 |
| 日夜貼圖互相污染 | direct 與 indirect 分開；夜間驗證白天亮斑未殘留，lightmaps 按預算載入 |
| 參考圖具有非物理光影 | 清楚標示藝術增強，用畫面一致性與使用者接受驗收，不宣稱精確物理重現 |
| 模型／材質來源不明 | 使用自製或授權清楚的資產；在下載或加入 repo 前記錄來源及使用條件，不以可下載當作可再散布 |
| 切換釋放問題 | GLB 準備與挂載分開，明確 ownership 與 cancellation，保留上一景直到新景可用 |

## 11. 本輪結論與下一步

本輪沒有正式 `.blend`、GLB 或新效果成品，沒有啟用排程。已確認的只是 Blender 版本、正在執行、隔離 Python 程式可執行，以及 glTF 匯出 operator 存在；MCP 與 GPU 渲染尚未驗證。

使用者確認本計畫後，下一步只做 **P0 + P1 + P2 樹影單景基準**。先交付 Blender／網站對照，達到圖像標準後才進入動態、魚與海景。
