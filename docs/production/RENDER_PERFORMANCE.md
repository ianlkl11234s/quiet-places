# 渲染效能調查紀錄

2026-09-27。起因：使用者問「網站效能還可以嗎？」，接著要求「根本優化解，不影響整體呈現，但可以提升效能」，並指定要看後處理。

本頁記錄這次探索過的全部方向，包括採用的、沒採用的，以及量測時踩到的坑，讓之後的效能工作不必重來一次。原始數據與比對圖在 [`exports/render-perf/`](../../exports/render-perf/README.md)。

## 結論摘要

- **瓶頸是 GPU 填充，主要來自 MSAA。** 在 Apple M3 加 Chrome（WebGL 經 ANGLE 轉成 Metal）上，MSAA 的成本大約和取樣數成正比：4 倍取樣約是單取樣的 3 倍。陰影更新、CPU 送繪製指令（1–2 ms）、draw call 數量都不是主因。
- **MSAA 的成本集中在特定物件**，不是整個畫面平均分攤。例如雨後天井的主模型約佔 58 ms、樹影午後的光線那組物件約佔 23 ms。
- **採用的只有「畫面不變」的部分**（見下一節），約一半的場景快 5–35%，最重的幾個場景幾乎沒改善。
- **SMAA 雖然快很多，但會讓比像素還細的細節斷裂**，所以不採用。使用者看過後決定「先這樣好了」：MSAA 2 倍、SMAA 都不當預設；個別場景的優化目前看起來還不需要，列為未來候選。

## 採用（PR：claude/render-perf）

| 改動 | 位置 | 畫面 | 效果 |
|---|---|---|---|
| 只有畫場景那一步做 MSAA：解析一次後再接 bloom 和輸出，後處理畫布改成單取樣 | `src/player/RenderPipeline.ts` 的 `SceneRenderPass`、`src/main.ts` 的 `updateAntialiasing()` | 相同。階光之間只有 0.07% 的像素差超過 16/255 | 向海的隧道 28→18、潮風商店街 34→28、雪光長廊 41→33、海邊小站 55→50 ms；雨後天井、階光之間、水光之間在誤差內 |
| 瀏覽器畫布改成 `antialias:false` | `src/main.ts` | 相同。composer 是先畫在另一張畫布上，這個抗鋸齒本來就用不到 | 省記憶體和一次解析 |
| 比較用的網址參數 `?aa=msaa2`、`?aa=smaa` | `parseAntialiasing()` | 預設不變 | 方便以後重新比較 |

原本的做法把 MSAA 開在 composer 兩張輪流使用的畫布上，所以 bloom 最後疊加光暈時，也是寫進多重取樣的半浮點畫布。改成只有場景做 MSAA 後，這部分的成本就不見了；但大部分的成本其實在場景本身的多重取樣，所以整體改善有限。

## 量過但沒採用

| 方向 | 量測結果 | 沒採用的原因 |
|---|---|---|
| 不做 MSAA，改用 SMAA，解析度 1.5 倍 | 每幀約省 50–65%（海邊小站 49→15、雨後天井 79→25 ms） | 比像素還細的細節斷裂：錦鯉鰭條變成斑點、階光之間的牆面裂縫變成鋸齒、細樹枝變成虛線 |
| SMAA 搭配原生 2 倍解析度 | 細節接近原樣；耗時和現行差不多，有的場景更慢（階光之間 84、雪落海窗 61、水光之間 106 ms） | 沒有變順 |
| MSAA 2 倍 | 大多數場景約省 30%（海邊小站 49→34、雨後天井 79→48 ms） | 邊緣稍微差一點；使用者決定維持現狀，只保留成網址參數 |
| 每個場景剛載入時自動量測，自動挑抗鋸齒方式和解析度 | 做成原型後可以正常運作 | 自動挑到的會是 SMAA 或較低解析度，都會改變畫面；而且量測時會短暫卡住畫面 |
| Bloom 內部解析度減半 | 沒有實作 | Bloom 的模糊核以內部像素計算，解析度減半會讓光暈範圍變成兩倍寬，改變畫面 |
| MSAA 畫布改用 8-bit 格式 | 和半浮點相比只差 3–12% | 不是頻寬問題；而且 bloom 需要超過 1 的 HDR 值 |
| 快取陰影貼圖（不每幀更新） | 關掉陰影更新約 0 ms | 沒有效益（潮風商店街本來就只在光向改變時更新） |
| 合併海邊小站的灰模方塊（draw call 577） | CPU 送指令只有 1–2 ms | 沒有效益；等上材質時再一起處理 |

## 正式站的其他觀察（下載面，這次沒有改）

- Caddy 對 JS 做了 gzip，但所有檔案都沒有 `Cache-Control`。檔名帶雜湊的資產可以設成長期快取。
- 首次載入的 JS 約 190 KB（gzip 後），其中 three.js 佔 160 KB。
- 主要的大檔案：階光之間模型 26 MB、光照 EXR 25 MB（這次沒在下載紀錄中看到，未確認是否有載入）、潮風商店街模型 23 MB、天井 9.7 MB、長鰭錦鯉 9.6 MB。改用 KTX2 或 WebP 壓縮貼圖可能縮小很多，但要重新匯出並比對畫質。

## 量測方法與踩過的坑

- **每幀耗時的量法**：連續呼叫 `composer.render()` 16–20 次，再用 `gl.readPixels` 讀一個像素強迫等 GPU 做完，用總時間算平均。取 3 輪的中位數。
- **WebGL timer query（`EXT_disjoint_timer_query_webgl2`）在 ANGLE/Metal 上的數字不可信**：每幀量到 150–450 ms，但實際畫面是順的。
- **不能只呼叫 `renderer.render()` 到離屏畫布再讀預設畫布**：ANGLE 可能不會等那張離屏畫布，會量到約 1 ms 的假數字。要量完整的 `composer.render()`。
- **requestAnimationFrame 的頻率不能當流暢度**：它不會等 GPU，而這台螢幕是 120Hz，同一個場景會量到 72–120 次不等。
- **測試瀏覽器是 DPR 1**：用 2400×1350 × 1 倍來模擬 1600×900 × 1.5 倍（一般 Retina 使用者的像素量）。agent-browser 不能直接設定 DPR。
- **兩個 worktree 同時開 vite dev server 會壞掉**：`.worktrees/*` 的 `node_modules` 是指向主工作區的連結，兩個伺服器同時寫依賴快取，會載入兩份 three.js，模型裡的物件型別判斷失敗（錯誤訊息是「樓梯間缺少主鏡頭」），畫面變黑或少影子。要比較兩個版本時，各自 `vite build --outDir <暫存>` 後用 `vite preview` 開。
- **開啟「減少動態效果」截圖時，主程式會暫停**，只在有操作時才重畫，可能截到還沒畫完的畫面。逐像素比對時不要開這個選項，或確認兩邊都已經畫完。
- **自動挑「差異最大的區塊」做比對**，會挑到會動的東西（魚、草），而不是抗鋸齒造成的差異。要比較細節時，先把動態停住，或手動指定區域。

## 未來候選（使用者：「可能可以考慮，但目前看起來都還好」）

1. 針對個別場景的重物件：雨後天井的主模型（MSAA 下約 58 ms）、樹影午後的光線層（約 23 ms）、水光之間（整體約 55–100 ms）。方向是找出在 MSAA 下特別貴的材質或半透明層，例如把體積光改成單取樣後再疊加。每個場景要個別研究，並比對畫面。
2. 下載面：`Cache-Control`、貼圖壓縮。
3. 在手機、Safari、Windows 上重量一次。MSAA 成本和取樣數成正比這件事可能只發生在 ANGLE/Metal，其他平台的結論可能不同。
