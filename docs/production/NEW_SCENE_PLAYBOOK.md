# 新場景 Playbook

建立：2026-09-27。依據：9 個場景的製作紀錄、6 份實驗回顧、Q0–Q3 畫質輪，以及使用者的要求：「之後當我想要開新場景的時候，Agent 都能夠知道要幹嘛，而我只需要專注在描繪場景就好。」

**分工**：
- **使用者**：描述場景、看圖、做選擇。
- **agent**：其他所有事情，照本頁執行。
- 除非使用者另有指示，agent 不向使用者詢問本頁已經回答的問題。

相關文件的角色：
- [MASTER](../prompts/quiet-places-master.txt)：美術語言。
- [偏好](PREFERENCES.md)：已確認的個人選擇。
- [品質準則](SCENE_QUALITY_GUIDE.md)：「做到位」的標準。
- [畫質迭代流程](QUALITY_WORKFLOW.md)：從分支到 merge 的交付流程。
- 本頁：新場景從零到上線的「做什麼、按什麼順序、避開什麼」。

---

## 0. 使用者只需要提供這些

| 必要 | 例子 |
|---|---|
| 一句話的地方和感覺 | 「颱風過後的騎樓，午後」 |
| 參考圖（可選，1–3 張） | 自拍或 AI 生成圖都可以 |
| 主角（可選） | 「一隻海龜」「一叢芒草」；沒給的話，agent 提 2–3 個候選讓使用者選 |

其他全部由 agent 決定並寫進 brief，包括站位、主光、時段表現、材質、動態、音樂。使用者只在檢視點做選擇。

## 1. 開場：先讀，再寫 brief

1. 讀這些文件，不要載入全部歷史：
   - MASTER
   - PREFERENCES
   - 本頁
   - [能力索引](CAPABILITIES.md)
   - [品質準則](SCENE_QUALITY_GUIDE.md)
2. 開獨立 worktree 與分支：`.worktrees/<scene-id>`、`claude/<scene-id>`。主工作區不寫入。
3. 用 [場景模板](templates/scene.md) 開 `docs/scenes/<id>.md`。先把 brief 寫出來，內容包括：
   - 唯一主角、主光路、留白比例、最多一件不可能的事。
   - 參考圖的解讀：**參考圖只是構圖與氛圍的參考**，不能當貼圖，也不是可以量測的建築或植物資料；原圖不進 public。
   - **空間語意**：這個地方在真實世界裡周圍是什麼。例如走廊兩側有房門、門後有房間、窗外是什麼。少了這層，完稿常被說「不像 OO 空間」。
   - 沿用、調適、新研究三類清單：先查能力索引，不從零重做已有的東西。
   - 需要研究的主題（特殊生物、特殊光學）：先寫研究報告，每條附可查來源，標 A 文獻實測／B 模型近似／C 美術；查不到就寫「查無」。
4. **第一個檢視點（S1）**：把 brief 和一張灰模加上站位截圖交給使用者。**站位和主光方向先確認，才做細節**。

## 2. 空間與相機

- 先畫俯視關係，包括牆厚、門窗、開口、主角活動範圍，然後才建模。
- 站位驗收不能只看預設角度：
  - 可轉動的極限角度
  - 畫面邊緣與牆地接合
  - 直式、16:9、超寬三種畫幅
- 有方向性的口語描述要複述確認，例如「靠右站」曾被誤解成站位左移。
- 站位座標只屬於該場景，不要套用到別的場景。
- 相機、FOV、yawRange 寫在場景的 PlaceInstance。需要調參數時，仿照 `/tools/snowwindow-camera/`、`/tools/snowhall-studio/` 做試片工具，不要讓使用者反覆手改。

## 3. 光與時段

必須做到，每一項都有人踩過：

- **時刻只單向循環**：晨曦 → 正午 → 暮色 → 月夜，相鄰時段 2 秒。改時刻要**同時**帶動光向、強弱、色溫、光斑。
- **四個時段都要分得出來**：
  - 晨曦：低角度、暖色。
  - 暮色：更暖、更斜。
  - 月夜：要有**說得出來源**的光，例如月光斑、路燈、窗外的光。不能是全黑，也不能像白天壓暗。
  - 窗外的天空與景物要跟著時刻變化。檢查月夜窗外是不是真的變成夜景。
- **暗要有受光原因**：不要壓曝光、不要塗黑、不要用均勻 ambient 提亮。受光區周圍要有合理的反彈光；暗部裡的主體要讀得出形體。
- **窗洞光**：
  - 用硬陰影的平行光投在平地板上，會被誤讀成凸起的平台。
  - 陰天、雪天、北窗這類漫射光，用與開口同尺寸的面光（RectAreaLight）近似。
- 共用時刻曲線在 `src/systems/TimeOfDay.ts`。場景若有自己的日照循環，要自己校準晨曦的暖色。
- bloom 只給真正的高光。白色的鰭、葉、雪不能出現光暈；需要時用 `bloom.threshold` 覆寫。

## 4. 材質、貼圖、烘焙

- 近景主體要有 PBR 貼圖組。主要表面 2K，確認近景需要才升 4K；第一眼會看到的鏽斑或髒污至少 1K。
- 遠景不可以是灰盒子，至少要有色彩和門窗分割（可以用程序 shader）。
- 有 Blender 母檔的空間，一起烘 AO 或 lightMap。改了開口或幾何，要配對重新匯出 GLB 並重烘間接光。「GLB 生成成功」不代表 GI 已經更新。
- 裂縫、污漬要有凹凸或粗糙度差異，**優先烘進貼圖**。用 shader 即時重建曾經讓幀率減半。
- glTF 會丟掉頂點色的 alpha，風動權重這類資料要另外輸出成屬性，缺少時要拒絕載入。
- 浮點資料比較用容差；hash 不一致不代表美術參數不同。

## 5. 生物

先查能力索引裡能直接沿用的東西：

| 需要 | 沿用 |
|---|---|
| 魚類轉向、側傾、擺尾頻率、懸停 | `src/shared/biology/locomotion/` |
| 背深腹淺、光澤、鰭膜 | `src/shared/biology/fish-surface/` |
| 透明生物（水母、翼足類） | `AureliaShading.ts`、`ClioneShading.ts` 的做法：fresnel 邊緣加背光散射，**不用 transmission** |
| 水流、尾流、懸浮顆粒 | `VirtualFluid.ts` 的 `sampleFlow`、`MarineSnow.ts` |
| 既有物種 | [biology 索引](../biology/README.md)：錦鯉、長鰭錦鯉、青鱂、烏翅真鯊、南方魟、海月水母、裸海蝶、銀魚、玻璃魷魚、黑潮小魚、蝠魟、鯨鯊 |

新物種或重做模型時：

- 形態依據附可查來源。第一步先做**物種辨識特徵**，例如烏翅真鯊的黑鰭尖加淺色帶。
- 用 Blender 腳本重建，並可重現；參考 `blacktip_shark.py`、`stingray.py`。候選先輸出到暫存路徑，測試通過才替換 public。
- 已有兩個以上的消費者時，先寫**契約測試**，比對骨架、clip、節點、尺度。
- 三角面與 GLB 大小要記錄，參考值：單隻 ≤ 30k 面、≤ 2 MB。

動作與行為：

- 相位要由游過的距離或速度積分，**不要用 elapsed 固定時鐘**。
- 轉彎要側傾加彎曲；低速時朝向保持；俯仰要設上限，不能垂直。
- 動作要先講得通，再處理防穿透。柔軟的鰭不能像硬支架一樣把身體撐起來；曾被否決的「撐竿跳」就是這個問題。
- **牆、窗、地板、天花板一律不可穿透**。生物從鏡頭後方進出，不能從暗牆生成或消失。
- 路線不擋鏡頭，會出現在光暗交界；群體要有停頓、滑行、異步，不要全群追著鏡頭。
- 用**正式視距**檢查輪廓與附肢。近看做得好，不代表在場景裡看得出來；只有十幾個像素時，調整路線或尺度，不要加亮。
- 數量和物種是使用者的決策，可能中途整個拿掉。被拿掉的模型和資料保留、不啟用。

## 6. 動態與生命感

- 整體要一直有細微的動：水、光、草、生物都在動，但**不同頻**，大部分時間接近靜止，偶爾有事件。
- 風：以微風到小風為主，偶爾陣風，形變要柔軟、有延遲，根部穩定。
- UI 或入場動畫不能「像預設動畫」。先查物理公式再做；帶回彈的 keyframe 已被否決過。

## 7. 播放器接線與效能

- 透過 `metadata.ts` 和 `catalog.ts` 註冊，實作 PlaceInstance；不要另建 registry，也不要自己跑 RAF。
- 填充率重的場景（體積光、全螢幕水面、大貼圖），`msaaSamples` 先用 2。
- 用 `scripts/review/perf.sh` 量 fps 和 CPU，和 main 比較；p95 或 fps 掉超過 10% 要找出原因。

## 8. 檢視點與交付

| 檢視點 | 給使用者看什麼 |
|---|---|
| S1 | brief、灰模、站位截圖：確認站位與主光方向 |
| S2 | 光和材質：四時段四宮格（`scripts/review/capture.sh`） |
| S3 | 主角：近看、連拍、正式視距下的截圖 |
| S4 | 完整候選：比較頁、效能、需要決定的事項（最多列 4 件），並啟動本機預覽，給網址與 A/B 參數 |

- 每個檢視點都不停工：交出去之後繼續做不依賴答案的部分。
- 使用者否決時，**只移除被否決的項目**；只要求加回幾項時，只加回那幾項，不把整套已拒絕的方案帶回來。
- 證據狀態分開記錄：測試、browser、使用者確認、PR 合併、部署。baseline 一改變，舊的截圖敘述就失效。
- 交付網址前，重新確認 dev server 真的在跑，並做一次 HTTP 讀回。
- 使用者確認後，照 [QUALITY_WORKFLOW](QUALITY_WORKFLOW.md) §7：記錄偏好 → 整理歷史 → PR → 一般 merge → main 只做 fast-forward → 另外確認部署。

## 10. 資源與安全

- 記憶體：同時最多 2 條工作線開瀏覽器，每條只開 1 個 `--session`，用完就關；dev server 用完就 kill，**絕不 `pkill -f vite`**。
- 主工作區裡不是自己的檔案不要碰。破壞性的 git 操作前先停下來問。
- push、merge、部署都要使用者同意。本輪使用者已授權的是「開 PR，並以一般 merge 合併」。
