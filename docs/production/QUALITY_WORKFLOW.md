# 畫質迭代工作流程（之後都照這樣做）

建立：2026-09-27。來源：Q0–Q3 與水母專案的實際做法，經使用者確認「之後都要這樣，有更多的依循」。

本頁規定「一輪畫質改善」從評估到合併的固定流程。

- **品質標準**見[場景品質準則](SCENE_QUALITY_GUIDE.md)。
- **風格**見 [MASTER](../prompts/quiet-places-master.txt)。
- **個人選擇**見[偏好](PREFERENCES.md)。

本頁只規定流程與交付格式，不重複上述內容。

## 流程總覽

```
評估 → 計劃 → 分支 → 分項實作（候選）→ 逐項驗收 → 分項 commit
     → 最終驗收（矩陣＋效能）→ 比較頁 → 使用者決定 → 整理歷史 → PR → 一般 merge
```

## 1. 評估：先看，再寫

1. 在本機跑起所有受影響的場景，拍**四時段四宮格**（晨曦、正午、暮色、月夜；1600×900，headed Chrome）。
2. 生物要另外拍**連拍**（6–8 張，約 0.5 s 一張）和**近看**，並讀動作程式確認根因。截圖只是證據，結論要能指到 `檔案:行號`。
3. 對照 MASTER：「暗」是風格。問題通常出在以下幾類，而不是「太暗」：
   - 暗部沒有形體
   - 光說不出來源
   - 時段之間沒有差異
   - 材質或生物看起來像 CG
4. 證據存到 `exports/quality-review-<日期>/`，只放 jpg。

## 2. 計劃：分期、可退回、先守基準

1. 寫計劃文件，放在 `docs/production/`。每一項都要列出：問題、做法、層級（光／材質／幾何／畫質／生物的模型、材質、動作、行為）、難度，以及是否碰到使用者已確認的基準。
2. 分期原則：
   - 先做低風險修正。
   - 再做共用能力（一次做好、多個場景受益）。
   - 然後是各場景細部。
   - 最後才是模型重做。
3. 需要研究的主題（例如生物運動、水族館外觀）要先寫研究報告，附**可查的來源**，並標示 A 文獻實測／B 模型近似／C 美術。查不到就寫「查無」。
4. 如果使用者的要求和 MASTER 衝突，先寫出「本計劃的解讀」，說清楚要做什麼、不做什麼，再動手。使用者明確表示要偏離 MASTER 時，記進偏好。
5. 計劃文件底部要有**進度紀錄表**（日期／項目／狀態／commit）。每一批完成就更新。

## 3. 分支與隔離

- 在 `.worktrees/<名稱>` 開獨立 worktree 和分支，不在 main checkout 上改。
- 主工作區裡不是自己的未追蹤檔，一律不碰。
- 被替換的原始資產（GLB、blend、貼圖）備份到 repo 外的 `.local-backups/<review-id>/`，不放進 exports，也不 commit。

## 4. 分項實作：每一項都是候選

- 每項改動要有**單一開關常數**，設為 0 或關閉時回到原畫面。例如 `STAIR_CRACK_GROOVE`、`A7_KEEP_ROLL`、`WATER_ROOM_BOUNCE`。
- **使用者指定過的動作或構圖，預設保留**。計劃想改掉的，做成開關，讓使用者選。例：隧道魟魚的翻滾。
- 改外觀的數值要克制。驗收要量**暗部亮度前後**，確認黑位沒有被抬高；月夜要確認沒有發光感。
- 模型重做要先寫**契約測試**，比對新舊 GLB 的骨骼、clip、節點與尺度。全部一致才能替換 public 裡的資產。

### 平行作業規則

- 同時最多 **3 個 worker**，其中開瀏覽器的最多 **2 條**。每條只開 1 個 `agent-browser --session`，用完就 close。dev server 用完就 kill，**絕不 `pkill -f vite`**。
- 每個 worker 都要有明確的檔案 ownership 與禁改清單。共用檔（`src/main.ts`、`src/player/*`、`src/systems/*`、`docs/production/*`）由主 agent 處理。
- worker **不 add、不 commit、不 stash**。看到別人的髒檔不要碰。
- 兩個 worker 需要同一份文件時，只讓其中一個直接寫；另一個把段落寫到 `exports/.../doc-section.md`，由主 agent 合併。
- 平行截圖一定要用 `--session`，不要用 `--session-name`，否則會共用分頁、拍錯場景。

## 5. 逐項驗收與 commit

- 每個 worker 回報時要附上：
  - 改了哪些檔案（`路徑:行號`）
  - 數值，以及退回方式
  - before／after 截圖路徑
  - 測試結果
  - 「分 commit 對照」
- 主 agent 要**親自看**關鍵的前後對照圖，並跑相關測試，才能 commit。
- **一個 commit 只對應一個項目**。
  - 同一檔案混了多個項目時，要拆開。
  - 拆完後，每個 commit 都要能單獨通過 `tsc`。
  - 依賴順序要對：共用模組先 commit，消費者後 commit。
- commit 訊息要寫「做了什麼、數值、退回開關、候選待確認（項目編號）」。

## 6. 最終驗收

1. **效能**：用 `tests/waterlight-performance.html?place=<id>`（真實 app 和 composer，5 秒暖機加 15 秒取樣）量 main 和分支的 9 個場景，比較 fps、p95、CPU、三角面、draw calls。
   - 發現退步就用二分法找出是哪個 commit。修正後重量。
   - 超過 10% 的項目要說明原因；查不出來就寫「未隔離、待追」。
2. **矩陣**：main 與分支各拍一套 9 景四時段四宮格。
3. **全套檢查**：`npx tsc --noEmit`、`npm test`、`npm run build`、`npm run check:project`。已知失敗的測試要註明它在 main 上本來就失敗。
4. **比較頁**：`exports/quality-review-final/index.html`，內容包括：各場景並排對照與改動清單（附 commit）、生物近看、效能表，以及「需要你決定的事」。產生腳本和截圖腳本要跟著 commit。
5. 啟動本機預覽，把比較頁和各場景的網址（含 A/B 參數）交給使用者看。

## 7. 使用者決定之後

1. 把確認內容記進 [偏好](PREFERENCES.md)：日期、原話、範圍，以及哪些仍是候選。
2. 如有需要，重整 commit 歷史，讓每個 commit 只對應一個項目。舊分支保留為備份，等確認後再刪。
3. 推送分支，開 PR。
4. PR 描述要寫：範圍摘要、驗證結果、效能、已知限制、使用者確認紀錄。
5. **一般 merge**：保留完整的 commit 歷史；不用 squash、不用 rebase，也不 force push。
6. merge 前確認三件事：PR 顯示可合併、分支包含最新的 main、沒有失敗中的檢查。
7. merge 後，main checkout 只做 `git pull --ff-only`，不要做 reset。
8. main 合併後會觸發既有的部署流程。部署結果要另外確認，不能把 merge 當成部署完成。

## 8. 交付時要跟使用者說清楚的事

- 哪些已確認、哪些仍是候選、哪些評估後不做（附理由）。
- 驗證範圍：技術檢查、瀏覽器、使用者確認、實機、部署，這五項分開寫。
- 未完成的項目及原因。
- 需要使用者決定的事，最多列 4 件最重要的，其餘放在比較頁。
